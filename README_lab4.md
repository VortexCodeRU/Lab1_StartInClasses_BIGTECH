# Лабораторная работа №4. Порождающие паттерны (вариант 15, плейлист)

## Теория

Порождающие паттерны решают общую проблему: **создание объекта — это отдельная ответственность**, которую нельзя размазывать по клиентскому коду. Когда класс сам вызывает `new` с именем конкретной реализации, он жёстко зависит от этой реализации: заменить её можно только правкой исходников, а в тесте — нельзя подставить заглушку. Принцип единственной ответственности требует вынести создание в отдельное место, принцип инверсии зависимостей — чтобы клиент работал с интерфейсом, а принцип открытости-закрытости — чтобы новая разновидность добавлялась без правки существующего кода. Порождающие паттерны — типовые способы этого добиться, и каждый решает свою задачу: фабрика выбирает реализацию, строитель пошагово собирает сложный объект, прототип копирует готовый образец, пул переиспользует объекты.

Отдельно разбирается **одиночка (Singleton)** и его ограничения. Одиночка гарантирует единственный экземпляр класса и даёт к нему глобальный доступ через статическое свойство. Проблема в том, что зависимость становится невидимой: по сигнатуре класса не понять, чем он пользуется, а в тестах такую зависимость нечем подменить — конструктор закрыт, состояние живёт между тестами, и порядок выполнения начинает влиять на результат. Замена состоит из двух шагов: выделить интерфейс и передать реализацию через конструктор. Единственность при этом не теряется — её обеспечивает уже не класс, а точка сборки (метод `main` или конфигурация), где объект создаётся один раз и передаётся всем потребителям. Второй способ сохранить единственность без глобального доступа — DI-контейнер с жизненным циклом singleton: экземпляр создаётся один раз контейнером по конфигурации, а не статикой внутри класса. Отдельная проблема одиночки — потокобезопасность ленивой инициализации; в C# её решает `Lazy<T>`.

**Фабричный метод** выносит создание объекта в отдельный метод, возвращающий интерфейс: клиент вызывает метод и не знает, какой класс создан. Ветвление по типу при создании допустимо — где-то программа обязана выбрать конкретный класс, — но такое место должно быть одно, а не повторяться в каждом клиентском методе. Чтобы убрать ветвление даже из фабрики, используют **реестр** (`Dictionary<string, Func<...>>`): добавление разновидности сводится к одной строке регистрации, а не к правке `switch`. **Абстрактная фабрика** применяется, когда создаётся не один объект, а согласованное семейство (например, для партнёрского канала — свой отправитель, свой формат документа, свой расчёт комиссии); она гарантирует, что объекты из разных семейств не смешаются.

**Строитель** нужен, когда у объекта много параметров, часть необязательна, а проверка корректности возможна только после задания всех значений. Ключевое требование: проверка инвариантов выполняется в методе `Build`, и объект, нарушающий правила предметной области, не создаётся; строитель, который просто раскладывает значения по полям, задачу не решает — он лишь заменяет длинный конструктор длинной цепочкой вызовов. Сам создаваемый объект остаётся неизменяемым: поля заполняются в конструкторе, вызываемом из `Build`, и после этого не меняются. Для объекта с двумя-тремя полями строитель не оправдан — достаточно конструктора.

**Прототип** создаёт новый объект копированием готового образца; применяется, когда настройка дороже копирования или когда набор образцов задаётся данными, а не кодом. Основной вопрос при копировании — глубина: поверхностная копия переносит ссылки на вложенные объекты, и копия продолжает делить их с образцом, поэтому изменение вложенного объекта в копии меняет образец; глубокая копия создаёт новые вложенные объекты. Если вложенные объекты неизменяемы, достаточно поверхностной копии — это ещё один довод в пользу неизменяемых значений.

**Пул объектов** хранит заранее созданные объекты и выдаёт их по запросу, а после использования принимает обратно; применяется там, где создание дорого (подключение к БД, поток, большой буфер) или где частое создание и уничтожение нагружает сборщик мусора. Пул вводится только при измеренной выгоде: нужно измерить показатель без пула, внедрить пул, измерить повторно и сравнить; если разница в пределах погрешности — пул не нужен, потому что он добавляет состояние, требует возврата объектов и усложняет отладку. Отдельное требование — очистка состояния: объект, возвращённый в пул, обязан быть приведён в исходное состояние, иначе следующий получатель получит чужие данные; это типичный источник дефектов, который не обнаруживается при одиночном использовании.

Наконец, после внедрения фабрик и зависимостей в программе появляется **единственное место**, где создаются конкретные классы и собирается граф объектов, — точка сборки (обычно `main` или конфигурация приложения). Весь остальной код работает с интерфейсами и получает зависимости через конструктор.

## Что нужно было сделать

Все задания выполняются для своей предметной области — вариант 15, плейлист.

**Задание 1. Разбор одиночки и его замена.** Взять класс-одиночку из варианта (в нашем случае `PlayerSettings`, хранящий громкость и режим повтора статически), показать, как к нему обращается код, и сформулировать тест, который при такой реализации невозможен, с объяснением причины. Затем выделить интерфейс `IPlayerSettings`, передавать реализацию через конструктор и перенести создание в точку сборки. Написать тест, который стал возможен после замены, — он должен использовать подставную реализацию из третьей работы. В отчёте привести два способа обеспечить единственность экземпляра без глобального доступа: точка сборки и DI-контейнер с жизненным циклом singleton.

**Задание 2. Фабрика.** Объявить интерфейс фабрики и реализацию с реестром разновидностей (для плейлиста — трек, подкаст, аудиокнига). Клиентский код должен запрашивать объект у фабрики и работать с интерфейсом `IPlaylistItem`, а не с конкретными классами. Запрос неизвестной разновидности должен отклоняться с понятным сообщением — это проверяется тестом. На защите добавляется разновидность из варианта (радиопоток): должны измениться только новый файл и строка регистрации, клиентский код и существующая фабрика — нет. В отчёте указать, какие принципы проектирования реализует переход (SRP, DIP, OCP) и в чём именно.

**Задание 3. Строитель.** Реализовать строитель для сложного объекта из варианта (подборка плейлиста) не менее чем с пятью параметрами, часть из которых необязательна. Обязательные поля и инварианты проверяются в методе `Build`, нарушение отклоняется исключением; созданный объект неизменяем. Нужны тесты: сборка корректного объекта, отклонение при отсутствии обязательного поля, отклонение при нарушении инварианта. В отчёте — сравнение с конструктором: сколько параметров было бы и сколько из них необязательных.

**Задание 4. Прототип.** Реализовать копирование образца из варианта (шаблон еженедельной подборки: копия меняет дату и набор треков). Тест должен подтверждать независимость копии: изменение копии не меняет образец. Выбор между поверхностной и глубокой копией обосновать составом полей, а также показать, какие поля можно не копировать, потому что они неизменяемы.

**Задание 5. Пул объектов и измерения.** Выполнить измерение показателя из варианта без пула (время построения списка из 10 000 элементов с созданием нового объекта на каждый). Реализовать пул с методами получения и возврата объекта и очисткой состояния при возврате. Выполнить повторное измерение, в отчёте привести таблицу с двумя значениями и разницей. Тестом подтвердить, что объект, возвращённый в пул, не хранит данные предыдущего использования. Сформулировать вывод: оправдан ли пул в этой задаче по результатам измерений. Пул вводится только при измеренной выгоде; если измерения показали отсутствие разницы, пул не оставляется в рабочем коде.

После каждого задания прогоняются тесты из третьей работы: паттерны не должны менять поведение программы. В клиентском коде не должно остаться оператора `new` с именем конкретной реализации — создание сосредоточено в фабриках и точке сборки. На защите преподаватель называет новую разновидность, и студент добавляет её новым классом и одной строкой регистрации в фабрике.
